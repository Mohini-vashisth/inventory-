# Inventory & Manufacturing System — CLAUDE.md

## Project overview

Django 5.2 LTS app for a steel coil manufacturing business. Covers the full workflow:
raw material (coil) intake → order management → part cutting → step-by-step production tracking → dispatch.

Single Django app: `materials` inside the `inventory` project directory.

## Running the dev server

```bash
cd inventory
python3 manage.py runserver
```

Migrations:
```bash
python3 manage.py makemigrations
python3 manage.py migrate
```

## Key dependencies

- Django 5.2 LTS (upgraded from 4.2 on 2026-10-05, since 4.2's extended support ended in April 2026; 5.2 is supported until April 2028 — the next LTS is the one to move to after that), django-jazzmin (admin theme), qrcode + Pillow (coil QR tags), reportlab (official PDF quotations — see "Official PDF quotation" below), python-dotenv, djangorestframework, whitenoise (static files in production), gunicorn (production WSGI server)
- Requirements are split by purpose, all pinned to what production runs (office PC: Python 3.12): `requirements.txt` (runtime only), `requirements-import.txt` (adds `pandas`/`openpyxl` — only needed for `manage.py import_excel` and its tests, so a normal deploy doesn't pull in pandas/numpy; `import_excel` fails with a clear "pip install -r requirements-import.txt" message if they're missing), `requirements-dev.txt` (adds `ruff`; what CI and local development install). `python-dotenv` was unpinned until 2026-10-05.
- **Django upgrade notes (4.2 → 5.2):** no code or migration changes were needed — no new migrations to apply (`migrate --plan` was empty, so rolling back is just `git checkout` of the previous commit plus a reinstall), no deprecation warnings under 4.2 beforehand, `collectstatic` unchanged. The one real risk was `django-jazzmin` 3.0.1, whose metadata only lists Django up to 5.0 (it declares no upper bound, so it installs fine, it just isn't officially tested against 5.x) — `AdminSmokeTests` renders every registered admin changelist/add/change page against sample records to guard that, and is the first place to look if an admin page breaks after a future Django or jazzmin bump. Local development needs Python 3.10+ (Django 5.x dropped 3.9; the stock macOS `python3` is 3.9, so use e.g. Homebrew `python3.11`); production and CI run 3.12.

## Deploying to a real machine (not local dev)

Local dev (`DEBUG=True`, `manage.py runserver`) skips several things a real deployment needs:

1. Set `.env` from `inventory/.env.example` — at minimum `DJANGO_DEBUG=False`, a real `DJANGO_SECRET_KEY`, and `DJANGO_ALLOWED_HOSTS` set to the machine's hostname/IP. Also fill in the `COMPANY_*` vars with real business details — see "Official PDF quotation" below.
2. `python3 manage.py collectstatic --noinput` — with `DEBUG=False`, `runserver` no longer serves CSS/JS itself. WhiteNoise (already in `MIDDLEWARE`) serves whatever `collectstatic` gathers into `staticfiles/`. Re-run this after any static-asset change.
3. Run under a real WSGI server, not `runserver` — the dev server isn't hardened for unattended use. `requirements.txt` installs the right one per OS automatically (environment markers): `gunicorn` on Mac/Linux, `waitress` on Windows — **gunicorn does not run on Windows at all**, it depends on Unix-only OS features.
   ```bash
   # Mac/Linux
   gunicorn inventory.wsgi:application --bind 0.0.0.0:8000

   # Windows
   waitress-serve --host=0.0.0.0 --port=8000 --threads=12 inventory.wsgi:application
   ```
   `--threads=12` (waitress defaults to 4) — sized for concurrent use across gate entry, coil picking, and production-step updates once more than a handful of people are on the app at once (e.g. a second plant, or heavier per-step logging from a future QA module); raise further only if a real slowdown is actually observed under peak concurrent load.
4. Schedule `python3 manage.py backup_db` (cron/Task Scheduler, e.g. nightly) — backs up `db.sqlite3` to `db_backups/` with a timestamp and prunes anything older than `--keep-days` (default 30), and also mirrors uploaded files (`MEDIA_ROOT`) into `db_backups/media/`. It uses SQLite's online backup API (`sqlite3.Connection.backup`), **not** a file copy: the DB runs in WAL mode, where recent commits can sit only in the `-wal` file, so a raw `shutil.copy2` of `db.sqlite3` silently produces an incomplete backup (`BackupDbCommandTests` proves this against a WAL-mode DB).

### Office PC: the app runs as a Windows service (`InventoryApp`, via `nssm`)

On the office PC, `waitress-serve` above isn't run by hand — it's wrapped as a Windows service named `InventoryApp` via `nssm` (`C:\Users\MATTA\Desktop\nssm-2.24`), so it survives reboots and doesn't need an interactive login session. Repo lives at `C:\Users\MATTA\Desktop\inventory-` (the office PC's Windows user is `MATTA`/`mdw\matta` — a different path than the home PC's `lm110` user mentioned in the global remote-access instructions).

**Deploying: run `scripts\deploy.ps1`** (from an elevated shell — an SSH session to the office PC already is):
```
ssh officepc "powershell -ExecutionPolicy Bypass -File C:\Users\MATTA\Desktop\inventory-\scripts\deploy.ps1"
```
It does, in order: refuse if tracked files have local changes → `git pull --ff-only` → `pip install -r requirements.txt` → `manage.py check` → **`backup_db` (aborts the deploy if the backup fails)** → stop the service → `migrate` → `collectstatic` → start the service → poll `/employee-login/` until it returns 200 (30 s). Paths come from the script's own location, so it isn't tied to this one checkout. On any failure it prints the previous commit (for `git checkout <hash>`) and the pre-deploy DB snapshot path, and restarts the service if it had already stopped it, so the plant isn't left without the app; it never rolls back automatically (a half-applied migration plus an automatic code rollback is how data gets lost).

Why it uses `sc.exe` rather than `nssm`: **`nssm restart`/`nssm status` hang indefinitely over a non-interactive SSH session on this machine** — confirmed with a deliberately wrong service name, which hung identically instead of erroring, so it's not a naming issue. The likely cause is `nssm` triggering a UAC elevation prompt on the office PC's own desktop with nobody there to click it. `sc.exe` doesn't elevate and returns immediately. By hand:
```
sc stop InventoryApp
sc start InventoryApp
sc query InventoryApp   # STATE 4 RUNNING once it's back up
```

**Nightly backup (office PC):** Task Scheduler task `InventoryDbBackup` runs `scripts\backup_db.bat` daily at 02:00 as `SYSTEM` (set up 2026-10-05; before that no backup was scheduled and `db_backups\` was empty). The `.bat` runs the venv's `manage.py backup_db` and appends output to `db_backups\backup.log`. Check it with `schtasks /query /tn InventoryDbBackup /v /fo LIST` (`Last Result: 0` = fine) or trigger one with `schtasks /run /tn InventoryDbBackup`. **The task has vanished once, cause unknown** (2026-10-05, about a minute after its first successful run; `backup.log` went with it, and a user was logged in at the PC's console at the time). It was recreated the same day and the Windows Task Scheduler operational log was switched on (`wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:true`, it's off by default) — so if it disappears again, look there for **Event ID 141 (task registration deleted)** with the account that did it: `wevtutil qe Microsoft-Windows-TaskScheduler/Operational /c:20 /rd:true /f:text /q:"*[System[(EventID=141)]]"`. Worth a glance at `schtasks /query /tn InventoryDbBackup` after any visit to that PC. **Media is backed up too:** the same run mirrors `inventory\media\` (customer POs, WhatsApp drawings) into `db_backups\media\` (`Command._mirror_media` in `backup_db.py`) — incremental, copying only new/changed files, and it **never deletes from the mirror** (a file removed from the live folder by mistake stays recoverable; unlike DB snapshots, mirrored media isn't pruned by age). **Known gap:** backups live on the same disk as the database, so they don't survive disk loss — copying `db_backups\` (DB snapshots *and* the media mirror) somewhere off the machine is still open.

### SQLite tuning: WAL mode + a longer write-lock timeout

SQLite's default journal mode locks the whole database file for the duration of a write and blocks readers while it does — invisible at today's single-plant, one-writer-at-a-time volume, but the first thing that would actually slow down once concurrent writers become routine (a second plant, or a future QA module logging more rows per step). Two changes address this, both already in place:

- **WAL mode**, enabled once per connection in `materials/apps.py::_enable_sqlite_wal_mode` (via the `connection_created` signal) — lets readers proceed without waiting on an in-progress writer. It's a persistent property of the database file itself (set once, stays set), but re-asserting it on every connection is cheap and guards against ever silently losing it — e.g. a fresh `db.sqlite3` on a newly set up machine that nobody remembered to flip.
- **A 20s write-lock timeout** (`DATABASES['default']['OPTIONS']['timeout']` in `inventory/settings.py`, up from SQLite's 5s default) — how long a write waits on SQLite's single-writer lock before raising "database is locked," instead of failing fast under load that's still well within what this app should handle.

Neither of these is a substitute for actually migrating off SQLite if it's ever needed — see "Why `db.sqlite3` isn't tracked in git" below for that discussion. They just push that point much further out.

### Hosting decision: on-site at the plant, not cloud (revisit if this changes)

Decided 2026-09-07. The whole app — code and `db.sqlite3` together — runs on one machine at the plant, not split across cloud + on-site or hosted purely in the cloud. Reasoning:

- The database needs to physically stay on-site.
- Splitting app (cloud) from database (on-site) was considered and rejected — every request would round-trip to the plant over the internet, the plant's connection becomes a single point of failure for *everyone* including remote users, and it costs more than either pure option while getting the reliability of neither.
- Pure cloud hosting was considered and rejected for now — it would mean plant employees lose access entirely if the plant's internet drops, even though they're standing next to the machines the app tracks.

**For the owner's remote access**: install [Tailscale](https://tailscale.com) on the plant machine and on the owner's devices (free tier: up to 6 users, unlimited devices). This puts the owner's phone/laptop virtually on the plant's LAN — they reach the exact same app and database as someone on-site, from anywhere, without exposing anything to the open internet. Once set up, add the plant machine's Tailscale hostname (looks like `<machine-name>.<tailnet-name>.ts.net`) to `DJANGO_ALLOWED_HOSTS` in `.env` alongside its LAN IP.

If this ever moves to the cloud instead, the deployment steps above (WhiteNoise, gunicorn, `.env`) carry over unchanged — the only new work would be picking a host and, if the platform doesn't offer real persistent disk, migrating off SQLite to Postgres.

### Public quote form: Tailscale Funnel, scoped to `/quote/*` only

Decided 2026-09-14, **switched from Cloudflare Tunnel to Tailscale Funnel on 2026-09-21** (see below for why). The customer-facing quote form (`/quote/<token>/`) needs to be reachable from outside — by people who aren't on Tailscale — without exposing the rest of the app (admin, employee portal, API) to the public internet.

Rejected approaches:
- **Exposing the whole app publicly** — the employee portal (PIN-only) and admin login would then be open to credential-stuffing/brute-force from anywhere, not just the plant network.
- **Migrating `mattadrawing.com`'s DNS to Cloudflare** — the domain's DNS is managed by the hosting provider behind GoDaddy (nameservers `ns1/ns2.md-19.webhostbox.net`, a cPanel host), and that same account also serves the company's live website and email plus five other Matta-Drawing-portfolio sub-brand sites (steelchamfer, keysteel, page3city, accurateassociates.in, truefoodo, ~99 DNS records total across all of them). Moving the whole zone risked breaking all of them over one mistyped or missed record — confirmed dangerous in practice: when this was actually attempted, Cloudflare's automatic DNS scan during "Connect a domain" only detected 18 of the real 99 records (missing DKIM/SPF/SRV/CalDAV/CardDAV/autodiscover and the entire DNS presence for the sub-brand sites), and there was no zone-export option in cPanel to fill the gap safely. Migration was abandoned at that point, before any nameserver change was made.
- **The original Cloudflare Tunnel setup (below, live 2026-09-14 to 2026-09-21)** turned out to depend on a newer Cloudflare dashboard flow ("Published application routes") that only works once a domain is a Cloudflare-connected zone — which `mattadrawing.com` never was. After an office-PC restart broke the tunnel's connector, reconnecting it was a dead end: the classic "any external domain via a CNAME to `cfargotunnel.com`" mechanism used originally was no longer reachable through the current dashboard for a non-connected domain, and fixing it forced the DNS-migration question above. Given the risk just found in that path, Tailscale Funnel (already-installed infrastructure, zero DNS changes) replaced Cloudflare Tunnel entirely instead.

What's actually in place: **Tailscale Funnel**, a path-scoped public-exposure feature of the Tailscale client already installed on the plant PC for the owner's remote access (see the hosting-decision section above). Set up with:
```
tailscale funnel --bg --set-path /quote http://localhost:8000/quote
```
This exposes only `https://<machine-name>.<tailnet-name>.ts.net/quote/*` to the public internet — currently `https://mdw.tail2734e7.ts.net/quote/*` — forwarding to Django's `/quote` path locally. Nothing outside `/quote/*` on that hostname is routed anywhere; the rest of the app (admin, employee portal, API) stays reachable only over plain Tailscale, exactly as before. Funnel needed a one-time enablement per tailnet (dashboard prompt at first run: `https://login.tailscale.com/f/funnel?node=<node-id>`) — after that, the `tailscale funnel` command above is what to rerun if the plant PC restarts and the background funnel doesn't come back on its own (check with `tailscale funnel status`).

**No DNS changes at all** — `mattadrawing.com`'s zone was never touched by this, unlike the Cloudflare CNAME approach. The public hostname is Tailscale's own `*.ts.net`, already valid and HTTPS-certified by Tailscale.

**Funnel needs the public origin trusted for CSRF** (found 2026-10-05, when every customer "Submit request" on the order form returned 403): Funnel forwards plain HTTP *without* an `X-Forwarded-Proto` header, so Django sees `http://` while the browser's `Origin` is `https://mdw.tail2734e7.ts.net`, and the origin check fails (`Origin checking failed ... does not match any trusted origins` in `logs\service-error.log`). Viewing the form worked, which is why it went unnoticed — only the POST is checked. Fixed by trusting `PUBLIC_QUOTE_BASE_URL` automatically (`PublicQuoteFormCsrfTests`). If a submit 403s again, that log line says why.

One setting this depends on (`inventory/settings.py` via `.env`): `PUBLIC_QUOTE_BASE_URL=https://mdw.tail2734e7.ts.net` fixes the link in quote-request emails (`materials/views/quotations.py::_dispatch_quote_email`) to always point at the public Funnel hostname regardless of which host the admin happened to be browsing on — without it, `request.build_absolute_uri()` would build the link from the admin's own (Tailscale-only) request host, producing an email link no external customer could ever open. `DJANGO_ALLOWED_HOSTS` must include `mdw.tail2734e7.ts.net` for Django to answer on that hostname at all. Live-verified 2026-09-21: the quote form is reachable end to end (Funnel → app) from a real external device, and a company added via the Orders/Query dashboards gets a `mdw.tail2734e7.ts.net` link in its quote email, not the old Cloudflare-era `quote.mattadrawing.com` one.

### Why `db.sqlite3` isn't tracked in git

It was committed and untracked twice before (`git log` shows both flips, each reverted within days) — untracking it broke a workflow where the database was being passed between machines via `git pull`/`push` in lieu of a real deployment. Now that the app runs as one persistent instance rather than being re-cloned onto different machines, that workflow no longer applies: `git pull` only touches code, and `db.sqlite3` sits on the deployed machine untouched by git, backed up separately via `backup_db`. **If you ever go back to syncing data between machines via git, this file needs to be tracked again** — the two reverts weren't accidents.

## Importing from the client's spreadsheet (`materials/management/commands/import_excel.py`)

`import_excel` fully replaces every `Material` row on each run (delete-all + reimport in one transaction) — it's a one-time/occasional full reimport tool, not routine syncing, since a coil's `coil_no` may already be printed on a physical QR tag by the time you run it again. `--reset-sequence` additionally rewinds `coil_no` to start counting from 1 — deleting rows alone doesn't rewind SQLite's autoincrement counter, so without this flag newly imported coils keep counting up from wherever the old ones left off (this is why coil numbering on a machine that's had earlier test data can start well above 1). **Only use `--reset-sequence` if nothing in the current data has a printed QR tag yet** — every coil gets renumbered.

The real client sheet has extra columns beyond `COLUMN_MAP` — `ISSUED QTY 1`, `ISSUED QTY 2`, `ISSUED QTY 3` — recording how much of a coil was already issued/used before this app existed. These are summed into `Material.legacy_used_weight` on import (0 if the columns are missing or blank), so a coil's used/unused status correctly reflects real-world history from day one instead of every freshly imported coil looking "Unused" regardless of prior usage.

## Architecture

### Code layout: views are a package, one module per area (`materials/views/`)

`materials/views.py` was one ~1,800-line file until 2026-10-05; it's now split so each area can be read and reviewed on its own. `materials/urls.py` imports the modules directly (`from .views import auth, gate_entry, ...`) and routes to e.g. `auth.employee_login`; `views/__init__.py` deliberately re-exports nothing.

| Module | What's in it |
|---|---|
| `common.py` | Small helpers shared by several modules (`_safe_next`, `_first_form_error`, `_first_formset_error`, `_safe_get`, `_parse_coil_no`, the over-commit exceptions). Everything else depends on it; it depends on nothing. |
| `auth.py` | Employee PIN login/logout (with the per-IP throttle), admin login, `home`, `employee_landing` |
| `gate_entry.py` | Gate entries, lots, registering coils, QR tag, the company/vendor autosuggest |
| `picking.py` | Order-first coil picking: `select_order`, `select_coil_for_order`, `pick_coil_for_order`, spec matching |
| `production.py` | `job_detail`, the scan gate `select_job_for_coil`, the read-only `production_board` |
| `queries.py` | Query dashboard, `query_edit`, `query_not_interested` |
| `quotations.py` | `quotation_form` (Send Quote / Save Draft), drafts, discard, PDF download, `_dispatch_quote_email`, `_public_quote_base_url` |
| `orders.py` | Order dashboard and confirm/reject/dispatch, `customer_autocomplete`, and the customer-facing `quote_form` |
| `media.py` | `serve_media` (staff-only uploads) |
| `whatsapp.py` | The whole WhatsApp bot: webhook, sending, media download, the question sequence |

Rules that keep this working:
- **Dependencies only point one way:** everything may import `common`; `orders` and `queries` import `quotations` (for `_public_quote_base_url`); `queries` uses `whatsapp`. No cycles — if two modules need the same helper, it goes in `common`.
- **Calls into `whatsapp` from other modules go through the module** (`from . import whatsapp` → `whatsapp._send_whatsapp_template_message(...)`), never `from .whatsapp import _send_...`. Tests patch `materials.views.whatsapp.<name>`, and a patch only takes effect if the caller looks the name up on that module at call time; a direct `from` import would bind its own copy and the mock would silently not apply.
- **New view?** Put it in the module for its area, add the access decorator (see "Two user roles"), and add the route to `urls.py`. `MaterialsRouteGuardTests` fails by name if the decorator is missing.

### Models (`materials/models.py`)

- **GateEntry** — one truck's delivery, logged from its invoice (vendor, vehicle no., invoice no., total weight) before any of its coils are individually registered. `vendor` is the raw-material *supplier* who delivered the truck — one per delivery. A truck can carry a mixed load of different coil *brands* though, so `company` (the brand/mill of the coil — e.g. "Tata Steel") lives on `GateEntryLot` instead, along with grade/size, since those can also vary lot to lot within one delivery. `total_weight` is the figure for the *entire* delivery. `no_of_coils()` sums every lot's coil count; `weight_per_coil()` is a rough average (`total_weight ÷ total coils across all lots`) — a paper reference, not a measurement, and less precise the more a delivery's lots vary in size. `coils_registered()`/`coils_remaining()`/`is_complete()` roll up the same stats from every lot
- **GateEntryLot** — one company(brand)/grade/size batch within a gate entry (e.g. "3 coils of Tata Steel EN8D 1.2mm"), all delivered by the same vendor (`GateEntryLot.gate_entry.vendor`). Its own `coils_registered()`/`coils_remaining()`/`is_complete()` cap how many coils can be registered against *that lot specifically* — New Coil Entry always targets a lot, never a gate entry directly, and always requires an open (incomplete) one — see Employee workflow below
- **Material** — raw coil inventory (grade, size mm, vendor, quantity kg, heat no). `weight_used()`/`weight_remaining()`/`is_used_up()` are the single source of truth for how much of a coil has been allocated to orders — admin, the REST API, and the coil-picking flow all call these rather than each computing their own aggregate. `weight_used()` = weight allocated via `OrderCoilPick`s **plus** `legacy_used_weight` (usage that happened before this coil was tracked in the app, imported from the spreadsheet's `ISSUED QTY 1/2/3` columns — see the import section below). `archived_at` marks a mistaken entry as archived (hidden from normal admin/employee views, excluded from coil picking) without ever deleting it or renumbering `coil_no` — that number may already be on a physical QR tag, so it's never reused or reassigned. `lot` links a coil to the gate entry lot (vendor/grade/size batch within a truck delivery) it physically came from (null for historical/imported coils, which predate gate entries); `invoice_weight` is that lot's parent gate entry's rough average per-coil figure, copied onto the coil at registration time — `quantity` remains the actual measured weight and is what every usage calculation (`weight_used()` etc.) is based on, never `invoice_weight`
- **OrderCoilPick** — one coil scanned/picked against an order's raw-material requirement (`materials/views/picking.py::pick_coil_for_order`). `weight_allocated` need not be the coil's full remaining weight — a coil can be split across multiple orders, the same partial-use philosophy `weight_used()` already applies. `output_equivalent()` converts `weight_allocated` into finished-product terms via the `AllowedCoilSpec.raw_material_ratio` matching this coil's grade/size under the order's product type (falls back to 1:1 if none matches)
- **GradeOption** / **SizeOption** — (a grade also has a `number`, 1–999, used inside product codes; see "Generated product codes" below) admin-managed lists of valid grades/sizes shown as tap-to-pick options on the Gate Entry form's lot rows (`/gate-entry/`); keeps the picker in sync without a code change. `manage.py backfill_options` (one-off, re-runnable) seeds these from every distinct grade/size already in `Material`, as-is — it doesn't try to merge differently-spelled duplicates (e.g. `EN8D` vs `EN-8D`), that's left for an admin to clean up afterward via the option admin pages
- **ProductCategory** / **ProductType** — **what the business calls a *product type* and a *product code*, which the code names get backwards.** A **product type** is a family of product the business sells and lives in the model **`ProductCategory`**. There are **7 since 2026-10-06** — Flat Bright Bar `FBB`, Square Bright Bar `SQB`, Profile/Shaped Bright Bar `PSB`, Cold Rolled Strip `CRS`, Cold Rolled Profile `CRP`, Chamfer Steel `CHS`, Triangle Bright Bar `TBB` — managed at `/admin/materials/productcategory/` (the owner adds others later: add or reorder there, no code change). They started as the 14 on the company website's Products menu (migration `0041`); migration `0045` reshaped that list, renaming Shaped Bright Bar and Steel Chamfer (taking the new letters only if no code started with the old ones) and deleting the rest unless a code hung off them. A **product code** is one of those types in a particular grade ("EN-8D Flat Bright Bar" = `FBB009`) and lives in the model **`ProductType`** (`item_code`, `category`, `grade`), an older name kept because renaming it would touch every table, field, URL and test; **the screens say "Product Type" for `ProductCategory` and "Product Code" for `ProductType`**. Each type has a fixed **3-letter code** (`ProductCategory.code`, unique, editable in the admin) — explicit rather than initials because initials clash. A code depends on type + grade only — **size is not part of it** (see "Width and thickness" below): `UniqueConstraint(category, grade)`, so a flat and a square bar in the same grade are different codes. A second, conditional constraint keeps the grade unique among codes that have no type yet (a database treats NULLs as distinct); `category` is nullable at the database level only for that reason, and the admin requires it for any code you save. `ProductType` has ordered ProcessSteps and AllowedCoilSpecs, and `item_code` is its identifying code. Renaming the models to match the screens (`ProductType`→`ProductCode`, `ProductCategory`→`ProductType`) is a known piece of debt, worth doing as its own change.
- **AllowedCoilSpec** — admin-configured coil grade/size that can be used as raw material for a ProductType. `raw_material_ratio` (default `1.000`) is "kg of this raw material needed to produce 1 kg of finished product" (e.g. `1.100` = 10% wastage) — since yield varies by which raw material spec is used, the ratio lives here rather than on ProductType itself, and it's what converts an order's `quantity` (an output weight) into how much raw material actually needs to be picked
- **ProcessStep** — one manufacturing step belonging to a ProductType (ordered)
- **ProductionJob** — links a picked coil (`OrderCoilPick`) to a ProductType + Order — one job per picked coil. `status` (`pending`/`in_progress`/`on_hold`/`completed`) is a rollup of its steps' latest StepLog, computed by `recalculate_status()` — the single source of truth, called from the employee step-update view and from `StepLogAdmin` (add/change/delete) so it stays correct no matter where a StepLog came from. A step logged `failed` (only possible via the admin — the employee portal only ever logs `in_progress`/`completed`) always puts the job on `on_hold`, shown to employees as a red banner on the job detail page, so a failed step can't silently look pending/in-progress forever
- **StepLog** — append-only log of step status changes for a job. `status` includes `failed`, settable only through the admin (`/admin/materials/steplog/`) — there's no "mark failed" action in the employee portal
- **Customer** — company name, email, phone, UUID quote token (regenerated after each form submission)
- **Query** — an inbound sales inquiry, logged before any `Customer`/`Order` exists — phone calls, word-of-mouth referrals, IndiaMART messages, WhatsApp, etc. `source` records how it came in — when logging by hand staff pick one of four (`Query.MANUAL_SOURCES`: **IndiaMART, Google, Referral, Other**), and two optional follow-ups hang off it: **Referral** takes `referrer_name` and `referrer_phone` (who referred them), **Other** takes `source_detail` (where from). `whatsapp` (what the bot records for a cold inbound message) and `call` (what older entries were logged as) stay valid values in `SOURCE_CHOICES` so existing rows still display, but they aren't offered when logging by hand — a phone-call lead is logged as Other with "phone call" as the detail. Follow-up fields are saved only for their own source, and are optional; `company_name`/`contact_phone`/`contact_email` and `drawing`/`drawing_notes`/`notes` capture whatever was already learned — `drawing` (an uploaded image/PDF, optional) and `drawing_notes` (the customer's own text if they didn't attach one) come from the WhatsApp intake bot's drawing question, see below. The bot also fills more answer fields — `gst_number` (15 chars, a valid GSTIN — **compulsory for every company, so there is no `NA`**; blank only means not collected yet, and a model validator rejects anything malformed on staff edits too), `gst_address`, `technical_requirements` (make / mechanical properties / process), `end_use` — listed once in `Query.INTAKE_TEXT_FIELDS`, which the detail page (via `gst_rows()` / `requirement_rows()`, blank rows included so it can show a dash), the edit form and the bot all read. The **Query dashboard shows only each query's name and number** (plus source, status, date and the action buttons); the Status cell also shows when the latest quote was sent ("Quote sent 05 Oct 2026") and, once it's been re-sent, "Rev N" with a link to all the quotes; everything else — contact, GST, product and requirements, drawing, notes, quotations — is on the query's own detail page (`query_detail`, see below), and every field can be edited on the Edit page. `status` moves **New → Quote Sent → Converted** (or **Not Interested**) — no staff-attribution field, matching how the rest of the app deprioritizes who-did-what tracking. `customer` is only set once a quote is actually sent (`quotation_form`, reached via `?query=<pk>` — see "Quote form flow"), mirroring how `Customer` itself is created on-demand elsewhere in the quote flow — before that, a query is just free-standing prospect info
  **Products live on `QueryItem`, not on the Query (multi-item queries, 2026-10-07).** A query holds 1–5 products (`Query.MAX_ITEMS = 5`, `query.items`, ordered by `position`; `Query.item_list()`). Each `QueryItem` has `product_category` (the product type), `product_type` (the product code, matched from type + grade), `grade`, `width`, `thickness`, `quantity` (kg) and `delivery_form` (Coil/Bar); `summary_text()` gives "Flat Bright Bar · EN8D · 50 x 6.5 mm · 500 kg · Coil". The old single-product columns on `Query` (and `quantity_text`) were removed by migration `0051`, which copies each existing query's product into one item (and copies the first item back on reverse). Questions asked once for the whole query stay on `Query`: company, email, GST, drawing, make/properties/process, end use. Everything that read the single product now reads the items: query detail (one card per product), Edit page (add/remove product rows with live code matching), dashboard ("N products"), the quote form (one line per product) and the customer's order form (one order per quoted line; delivery form pre-filled per line).
- **Quotation** / **QuotationLineItem** — a record of an official quotation, created via `quotation_form` (`/quotations/new/`, see "Quote form flow" below). Mirrors the client's real, pre-app quotation format: `Quotation` holds `status` (`draft`/`sent`) and header fields (`ref_no`, `rev_no`/`rev_date`, `sales_person`, `kind_attn`, `subject`, `customer_address`, `same_state_as_us`, `freight_amount`, `pf_amount`, and per-quote-editable Terms & Conditions fields with sensible defaults), and one or more `QuotationLineItem` rows hold the actual priced items (description, `category` (product type)/`product_type` (product code)/grade/size, quantity, unit, rate_per_kg, discount_pct, hsn_sac, gst_pct, tool_cost, moq) — a single quote can cover multiple grade/size combinations at once. **Immutable once `sent`** — correcting anything means sending a new quotation, not editing history — but a `draft` is the deliberate exception: freely editable and discardable until it's actually sent (see "Quote form flow"). `quotation_no` (displayed as `QUO-####`, or `'DRAFT'` via `formatted_no()` while unset) is only assigned when `status` flips to `'sent'` (in `Quotation.save()`) — sequential like `Order.order_no`, but — unlike `order_no` — **never renumbered or reused**: a sent `Quotation` is a permanent record of what was actually quoted, and an abandoned/discarded draft must never have consumed a number to begin with. `same_state_as_us` drives the GST split (`Quotation.cgst()`/`.sgst()`/`.igst()`): CGST+SGST (half the line items' combined GST each) if checked, all under IGST if not. `Quotation.total_amount()`/`.amount_in_words()` (Indian lakh/crore numbering, via `_indian_number_to_words` in `materials/models.py`) roll everything up. `sent_at` records when it was actually sent (set once when `status` flips to `sent`, never moved by later saves; `created_at` is when the draft was started) — the date printed on the PDF is the sent date. **Sending a quote again for the same query means the quote was updated**: every send is its own immutable `Quotation` (new `quotation_no`, nothing overwritten), and `Query.sent_quotations()` / `quote_revision()` / `quotation_history()` read them back oldest-first as revisions — the original is Rev 0, the first re-send Rev 1, and so on. Revisions are tracked per `source_query`, not per customer (a re-quote to an existing customer from the Orders dashboard has no query, so no revision chain). `source_query` links back to the originating `Query` when applicable (null otherwise) — see the query-status-doesn't-flip-until-sent note below. `QuotationLineItem.quantity`/`rate_per_kg` are nullable specifically so a draft row can exist with a product picked but the rate not agreed yet; a fully validated formset (via `QuotationLineItemFormSet`) is still required to actually send. The PDF itself (`materials/pdf.py::generate_quotation_pdf`) is generated fresh from the `Quotation` + its `line_items` every time it's needed — attached to the Send Quote email, or re-downloaded later via `/quotations/<pk>/pdf/` — never stored on disk, the same "derive it, don't persist it" approach `coil_tag.html` already uses for QR codes
- **Order** — customer requirement: product_type FK, grade, size, quantity, delivery date, status. `source_query` optionally links back to the `Query` that led to this order, set when the customer submits a quote form that was pre-filled from an in-flight query (null for orders that didn't originate from a logged query). `purchase_order` is an optional `FileField` the customer can attach on the quote form itself (their own PO, if they have one) — stored under `MEDIA_ROOT/purchase_orders/%Y/%m/`, downloadable from the admin's Order detail page. `order_no` (displayed as `ORD-####`) is a separate field from the primary key, assigned sequentially on creation and **kept gap-free**: deleting an order renumbers every order after it down by one, via a `post_delete` signal receiver (`_close_order_number_gap` in `materials/models.py`) that fires regardless of how the delete happens (admin single/bulk delete, `.delete()` on a queryset). This is the opposite of `coil_no`/`job_no`, which are deliberately *never* reused because they may already be on a printed tag — an order number is just an internal reference nobody prints ahead of time, so closing the gap was requested instead. One consequence: an order's displayed number **can change** if an earlier order is deleted, so don't treat `ORD-####` as a permanent identifier in code — use the primary key for that (`Order.pk`, used throughout `materials/urls.py`/views for routing)

### Order statuses
`pending` → `confirmed` → `in_production` → `completed` (or `cancelled`)

- **pending**: submitted via customer quote form, awaiting admin review
- **confirmed**: admin approved, ready for employees to pick coils against it
- **in_production**: first coil picked against this order
- **completed**: admin dispatched

### The order page (`/orders/<pk>/`)

Clicking an order on the Orders list (its number, the customer name, or **👁 Details**) opens `order_detail` (staff-only, `materials/views/orders.py`, `templates/materials/order_detail.html`) — the same idea as a query's detail page, replacing the old inline "Details ▾" row. Cards: the status with the Confirm / Reject / Dispatch actions that fit it (and the "no product code, can't be confirmed" and low-stock warnings), the customer (with links to the query and the quotation PDF it came from), the product (type, code, grade, width, thickness, tolerances), quantity and delivery (form with length or approximate weight, expected date, frequency), requirements and attachments (drawing and purchase order links, mechanical properties, processes, end usage, mill make, notes) and production (coils picked against the order and how much of the quantity is covered). The order numbers on the Query dashboard and query page link to it.

### Raw-material stock check on confirm

`Order.available_raw_material_output()` (`materials/models.py`) sums how much finished-product output the currently in-stock raw material could cover — across every `AllowedCoilSpec` on the order's product type (grade/size + ratio), or any non-archived coil with remaining weight if none are configured (same wildcard fallback the picking flow uses). `has_sufficient_raw_material()` compares that against `Order.quantity`; both return `None` if no product type is set yet (nothing to check against).

Checked once, at `order_confirm` (`materials/views/orders.py`) — not at quote submission, since the exact grade/size requirement is only locked in once a product type is assigned, which confirming already requires. If stock looks short, the admin gets an immediate `messages.warning()` on confirming, **and** a persistent "⚠️ Low stock" badge stays on that order's row in `/orders/` for as long as it's still true — scoped to `confirmed`/`in_production` orders only (not pending/completed/cancelled, where it isn't actionable). On-screen only, deliberately no email — the owner sees it browsing the dashboard, not in an inbox.

### Two user roles

**Access control is declared with decorators, not hand-written per view** (`materials/decorators.py`). Every routed view in `materials/urls.py` carries one of:
- `@employee_required` — session flag set by `employee_login` (shared PIN); otherwise redirects to `/employee-login/?next=<path>`.
- `@staff_required` — `request.user.is_staff`; otherwise redirects `home`. Takes `on_denied=` for a different refusal: the two dashboards use `redirect_to_admin_login`, and `customer_autocomplete` returns an empty JSON list.
- ...or is listed in `MaterialsRouteGuardTests.PUBLIC` (`materials/tests/test_auth.py`) with a one-line reason: `home`, `admin_login`, `employee_login`, `employee_logout`, `quote_form` (the UUID token is the credential), `whatsapp_webhook` (HMAC-verified inside the view).

`MaterialsRouteGuardTests` walks the URLconf, so **a new view with neither a decorator nor a PUBLIC entry fails CI by name** — the whole point, since previously a forgotten two-line guard was a silent unauthenticated hole. It also checks that anonymous requests, an employee-PIN-only session, and a non-staff login are all denied on every guarded route, and that the REST API rejects anonymous requests. When adding a view, add the decorator above the `def`; only add to `PUBLIC` for something that is genuinely meant to be open.

**Admin/staff** (`is_staff=True` Django user):
- Access via `/admin-login/` → Django admin (`/admin/`) or `/orders/` dashboard
- Can confirm/reject/dispatch orders, manage product types, view all data
- Materials list shows a Used/Unused status badge and filter (computed from allocated weight, not stored). A mistaken coil entry should be **archived** (bulk action in the admin), not deleted — archiving hides it from the materials list and from employee coil-selection/picking, but keeps its `coil_no` intact. Archived coils are hidden by default; `?archived=yes` or `?archived=all` in the admin URL shows them

**Employee** (PIN-based session):
- Access via `/employee/` — requires PIN (`EMPLOYEE_PIN` in `.env`)
- Login is throttled per client IP (`employee_login`, `settings.EMPLOYEE_LOGIN_MAX_FAILURES` = 5 wrong PINs, then locked out for `EMPLOYEE_LOGIN_LOCKOUT_SECONDS` = 15 min, even for the correct PIN; a successful login clears the count). Counts live in Django's default cache (`LocMemCache`, per-process — fine for the single waitress process, resets on restart). Keyed on `REMOTE_ADDR` only, never `X-Forwarded-For` (client-supplied, would let an attacker dodge the lockout). Trade-off: everyone behind one shared IP (e.g. several tablets behind one NAT) shares one counter, so five typos across them lock them all out for 15 minutes — restart the service (`sc stop`/`sc start InventoryApp`) to clear it early. A 4-digit PIN is still only 10,000 combinations; this makes guessing slow (~480/day per IP), not impossible — the portal is only reachable over Tailscale/LAN, not the public Funnel paths.
- Can register coils, pick coils against orders, update production step progress
- "Log out" button on the portal (`/employee-logout/`, POST-only) clears the session — the shared PIN stays valid, only that browser's login is ended

## Employee workflow

1. New Coil Entry — always starts with a gate entry, never a bare coil form:
   - Gate Entry → `/gate-entry/` — one page, one submission, for the whole truck. Top: date/vehicle no./**vendor** (the supplier)/invoice no./total weight. Vehicle no. is normalized to uppercase, letters/digits only, as you type (no fixed slot layout — real plates vary too much in segment length, e.g. RTO code can be 1-4 digits, series 1-4 letters, to force one); `GateEntryForm.clean_vehicle_no()` uppercases again server-side as a safety net for anything submitted without JS. Below: one or more **lots** (**company** — the coil's brand, grade, size, coil count — grade/size via the usual tap-to-pick overlay) rendered as collapsible rows, each summarized when collapsed; "+ Add Lot" appends another row (collapsing the rest) for a delivery mixing brands/grades/sizes, so the whole truck is logged in one go. Vendor and company are free text with autosuggest (`/gate-entry/autocomplete/?field=company|vendor&q=...`, `materials/views/gate_entry.py::material_field_autocomplete`) drawn from values already used in `Material` — keeps "Tata Steel" from also ending up as "TATA STEEL" and "Tata steel" across different gate entries. Each row past the first also has "✕ Remove This Lot" to undo one added by mistake before saving (client-side only — removing re-indexes the remaining rows so the formset's field names stay contiguous; at least one lot is required, so the button is hidden when only one remains). The GateEntry and every `GateEntryLot` row are created together, atomically (`materials/views/gate_entry.py::gate_entry_form`, backed by a `GateEntryLotFormSet`) — an invalid lot rolls back the whole submission rather than leaving a partial gate entry behind. Saving redirects to the gate entry's detail page.
   - Add Lot (later) → `/gate-entry/<pk>/add-lot/` — a single-lot version of the same form, for a delivery that turns out to have another grade/size/vendor beyond what was logged initially. Saving returns to the gate entry's detail page.
   - Gate Entry detail → `/gate-entry/<pk>/` — lists every lot logged so far with its progress, a "+ Add Another Lot" link, a link into coil registration for each lot that still has room, an "✏️ Edit" link to fix the gate entry's own top-level fields, and — for any lot with zero coils registered against it yet — a "✕ Remove (added by mistake)" action (`/gate-entry/lot/<lot_pk>/delete/`) to undo it after the fact. Once a lot has even one coil, the option disappears (`Material.lot` also uses `on_delete=PROTECT`, so a stray attempt would fail loudly rather than orphan real coils).
   - Edit Gate Entry → `/gate-entry/<pk>/edit/` (`materials/views/gate_entry.py::gate_entry_edit`) — the same date/vendor/vehicle no./invoice no./total weight fields as creation, reusing `GateEntryForm` bound to the existing instance. Unlike a lot or a registered coil, nothing here is locked once coils exist against it — these are paper/reference details, not something coil registration depends on being immutable — so it's editable at any point, before or after lots/coils are registered.
   - Select Gate Entry → `/gate-entry/select/` — lists every lot (across all gate entries) that still has coils left to register; "Add Another Coil" on the printed tag returns here once a lot is complete, or straight back into the same lot if it still has room.
   - Register a coil → `/gate-entry/lot/<lot_pk>/coil/` → prints QR tag. Vendor comes from the gate entry, company/grade/size from the lot — none of it resubmitted, so a tampered/stale form can't override them — shown read-only alongside the gate entry's `weight_per_coil()` (a rough average across every lot) for reference. The employee enters heat no. and the coil's **actual measured weight** (`quantity`) — deliberately separate from that paper `invoice_weight`, since real coils rarely weigh exactly the computed average, more so once a delivery mixes multiple grades/sizes. Once a lot's `no_of_coils` have been registered, it shows complete and blocks further entries against it — a new lot (or gate entry) is required for the rest.
2. Pick Coils for Order — an order isn't fulfilled by cutting a part from one coil; it's fulfilled by picking a number of whole (or partially-used) coils as raw material:
   - Select Order → `/select-order/` — lists confirmed orders (not yet started) and in-production orders separately.
   - Picking hub → `/order/<pk>/select-coil/` (`materials/views/picking.py::select_coil_for_order`) — shows the order's fulfillment progress (`Order.picked_output_weight()` vs `Order.quantity`), a coil-number field for scanning — either a dedicated barcode/QR hardware scanner (acts as a keyboard, just types the coil's tag text into the field) or the device's own camera (see the camera-scan section below), and a browse list of coils matching the order's `AllowedCoilSpec`s (all coils with remaining weight if none are configured). The browse list is sorted **best-fit first** — coils whose remaining weight is closest to what the order still needs (converted through that coil's matching spec ratio via `_ratio_for_coil`, same helper `pick_coil_for_order` uses for its suggested weight) are listed above coils that would over- or under-shoot by more, rather than just showing newest coils first. A client-side search box filters the browse list by coil no./grade/size/vendor (plain JS substring match against a `data-search` attribute on each card — no backend query, since the list is already fully rendered). Also lists every coil already picked for this order so far.
   - Confirm pick → `/order/<pk>/pick-coil/<coil_pk>/` (`materials/views/picking.py::pick_coil_for_order`) — shown after scanning or clicking a coil from the browse list. Suggests a weight capped at both the coil's remaining weight and how much raw material the order still needs (converted via the matching `AllowedCoilSpec.raw_material_ratio`), but the employee can adjust it down for a partial pick. Product type comes from the order, never resubmitted. Confirming atomically creates the `OrderCoilPick`, a `ProductionJob` for it, and one pending `StepLog` per `ProcessStep` — an invalid submission creates none of them. Blocked (with a clear reason) if the coil is archived, exhausted, doesn't match the order's allowed specs, the order's requirement is already fully picked, or the order has no product type set.
3. Update Progress — gated behind scanning/typing the coil's own number, the same way coil picking is gated behind scanning the coil being picked:
   - Scan gate → `/scan-job/` (`materials/views/production.py::select_job_for_coil`) — scan or type a coil number; looks up every `ProductionJob` linked to that coil via `ProductionJob.objects.filter(pick__coil=coil)`. Exactly one job → redirects straight into it. Zero jobs → error ("hasn't been picked for any order yet"). More than one (a coil split across multiple orders, so multiple `OrderCoilPick`s/jobs) → shows a small picker to choose which job.
   - `/job/<pk>/` to tick steps, one job per picked coil.
   - `/production-board/` is now **read-only** — an overview of every in-production order's jobs and current step, with a "📷 Scan to update" badge instead of a link (reachable from the scan gate's "View all jobs →", and vice versa) — this and the scan gate deliberately don't cross-link into `job_detail` directly, so updating progress always goes through the scan step.

### Camera QR scanning (`materials/static/materials/coil_scan.js`)

Both the coil-picking hub and the Update Progress scan gate offer a "📷" button next to the manual coil-number field that scans a printed QR tag with the device's own camera — shared logic (`coil_scan.js`) driven by a standard set of element IDs (`camera-scan-btn`, `scan-modal`, `scan-video`, `scan-modal-status`, `scan-modal-cancel`, `coil-no-input`, `coil-scan-form`) so both pages just point their markup at the same script rather than duplicating ~100 lines of camera/decode logic.

- **Decoding**: tries the native `BarcodeDetector` API first (Chrome/Samsung Internet on Android support this with no extra library); falls back to `jsQR` (vendored at `materials/static/materials/jsQR.min.js`, not loaded from a CDN — the plant's tablet shouldn't depend on outside internet to scan a coil) if `BarcodeDetector` isn't available. A decoded value fills the coil-number input and submits the form exactly as if it had been typed or scanned by a hardware reader — no special handling needed downstream.
- **HTTPS is required** — browsers refuse camera access (`getUserMedia`) on a plain-HTTP origin (the plant LAN's own IP). The tablet must reach the app via the Tailscale hostname (**`https://mdw.tail2734e7.ts.net:8443/employee/`** — see below for why the port; real HTTPS via Tailscale's own certs) rather than the LAN IP for the camera button to do anything; typing the number manually still always works regardless of HTTPS.
- **Why port 8443:** the plain `https://mdw.tail2734e7.ts.net/` (443) is the public Funnel and only forwards `/quote` and `/webhooks/whatsapp`, so `/employee/` there is a 404 (found 2026-10-08). Adding `/` to it would expose the admin and portal to the internet, so the whole app is served on a second, **tailnet-only** port instead: `tailscale serve --bg --https=8443 http://localhost:8000` (run on the office PC; `tailscale serve status` should show `:8443 (tailnet only)` and `tailscale funnel status` must not list it). Re-run it if the PC restarts and the entry is gone. Add `mdw.tail2734e7.ts.net` is already in `DJANGO_ALLOWED_HOSTS`; the port needs no change there.
- Falls back gracefully with an on-screen message ("Camera access isn't available" / "was denied") rather than breaking the page — manual typing (or a hardware scanner) remains the guaranteed-working path either way.
- Since these are static files (new, not previously part of the app), remember to `collectstatic` after deploying — see the deployment section above.

## Templates: `base.html` plus inline shared CSS

All 24 page templates `{% extends "materials/base.html" %}` (since 2026-10-05; each one used to carry its own `<!DOCTYPE>`/`<head>`/`<style>`). A page fills in blocks: `title`, `css` (that page's own CSS), `content` (the body), and optionally `body_attrs`. Shared rules live in `templates/materials/_base.css` and are pulled in by `base.html`'s `base_css` block; a page opts out by overriding that block with nothing (only `home.html` does — it never had the `*` reset the others use, and opting out keeps it pixel-identical).

**The shared CSS is inlined with `{% include %}`, deliberately not a `/static` file.** `quote_form.html` and `quote_submitted.html` are the customer-facing pages, reachable from outside only through the Tailscale Funnel path `/quote/*` — `/static/...` isn't exposed there, so an external stylesheet or script would 404 for customers and leave the page unstyled. `TemplateStructureTests.test_customer_facing_pages_load_nothing_external` fails if either page ever references `/static/`, a stylesheet link, or a script `src`. (The employee scanner pages do use `/static/` JS; they're only reached over Tailscale, where it works.)

**What is and isn't shared — the pages have diverged, on purpose.** `_base.css` holds only rules that were byte-identical in every template that defined them *and* whose class isn't used by a page that doesn't style it (so hoisting couldn't change any other page): the `*` reset, `.error-msg`, `.alert*`, `.muted`, `.form-row`/`.cols-2`/`.cols-3`, the `.autocomplete-*` set, and a few `:hover` rules. Everything else stays per-page, because the rest genuinely differs — `.card` has 9 variants across 15 pages and `body` 8 — so "one stylesheet" would be a visual redesign, not a refactor. Bare tag selectors (`table`, `td`, `input:focus`, `header`) also stay per-page: hoisting them would restyle pages that never defined them. Three visual families exist: the blue→green gradient employee/portal pages (16), the staff dashboards with a header bar on `#f4f6f9` (5), and standalone pages (admin login, the printable coil tag, home).

**How the refactor was verified, if a similar one is ever needed:** nothing in the test suite checks visuals, so every page (30 states including error states) was rendered before and after with sample data, loaded side by side in a browser at 1024/768/390 px wide, and the *computed style of every element* was compared (1,520 elements: 0 differences; the harness was first checked against a deliberately planted 1px change). The only intended difference is `<html lang="en">` on the admin login, which previously had none.

**The Copy Link button** (`_copy_link_script.html`, included by the Query dashboard, Query detail and Orders pages — never a private copy per page, `CopyLinkScriptTests` checks that) cannot rely on `navigator.clipboard`: it exists only on a secure page (HTTPS or localhost), and staff reach the app over plain `http://` Tailscale/LAN addresses, where it is undefined and the button did nothing (found 2026-10-07). It uses the clipboard API when `window.isSecureContext`, otherwise copies through a hidden text box (`document.execCommand('copy')`, which works on http), and if the browser refuses that too it shows the link in a `prompt()` to copy by hand. The tests run the real script in Node with a stubbed `document`/`navigator` (skipped without Node).

**Partials** are `{% include %}`d fragments, not pages, and are named with a leading underscore (`_base.css`, `_query_actions.html`, `_copy_link_script.html`); `TemplateStructureTests` skips them. **Adding a page:** extend `base.html`, put page-specific CSS in the `css` block, and only move a rule into `_base.css` if it's identical in 3+ pages and its class isn't used elsewhere without a rule. `TemplateStructureTests.test_every_page_template_extends_base_html` enforces the `extends`.

## Order-first coil picking (important constraint)

When an order has a ProductType with AllowedCoilSpecs configured, only coils matching those grade/size specs can be picked (`_coil_matches_order_specs` in `materials/views/picking.py`, used by both the scan lookup and the browse list). If no specs are configured, all coils with remaining weight are eligible. Orders **cannot be confirmed** without a product type set, and picking is blocked entirely without one.

## Query dashboard: unified lead intake (`/queries/`)

Before any formal quote exists, an inbound inquiry (usually a phone call) is logged as a `Query` via the **Query Dashboard** (`materials/views/queries.py::query_dashboard`). It deliberately does **not** link to `/orders/` — Queries and Orders are separate staff workflows, not a browsing path into each other. Manual logging asks for **source + phone number** (plus the optional referral/other details above, revealed by the form when Referral or Other is picked; the hidden fields are disabled so they aren't submitted) — nothing else is known yet, so nothing else is asked. Submitting it immediately fires an automated WhatsApp intake sequence (below) that gathers the rest directly from the customer. Everywhere `company_name` might be blank, code and templates fall back to `contact_phone` (or `f"Query #{pk}"` as a last resort): `Query.__str__`, `quotation_form`'s customer-name fallback for the `?query=` path, `QueryAdmin.display_name`, and the dashboard table's Company/Contact column.

- **`query_detail`** (staff-only, `/queries/<pk>/`, `materials/views/queries.py`) — a read-only page with everything known about one query, in cards: contact, GST, product & requirements (every intake field, with a dash where unanswered, plus the drawing link/note), notes, and a **Quotation history** card (anchor `#quotations`) listing every quote newest-first — drafts on top with "Resume draft", then each sent quote as Original / Rev 1 / Rev 2… with its sent date and PDF link, so every earlier version stays reachable. The dashboard's name links here, as does its "Details" button. It offers the same status-dependent actions as the dashboard (Edit, Send Quote, Copy Link, PDF, Not Interested) via the shared partial `templates/materials/_query_actions.html`, so the two pages can't drift apart; the Copy Link script is the shared partial `_copy_link_script.html`.
- **`query_edit`** (staff-only, `/queries/<pk>/edit/`) — fixes a wrong/incomplete field directly from the dashboard (a typo'd company name, a grade the WhatsApp bot mis-parsed, etc.) instead of needing Django admin for it. Edits `company_name`/`contact_phone`/`contact_email`/`product_type`/`grade`/`size`/`quantity`/`notes` (as on the quote form, the **Product Code is auto-filled** once product type, grade and size are entered — live in the browser from an embedded code map, never replacing a code picked by hand, and again on save via `_match_product_type` if none was chosen; the grade has the same type-ahead and is tidied to the listed spelling) plus every intake answer (`Query.INTAKE_TEXT_FIELDS`; the GST number is upper-cased and compacted) via `Query.full_clean()` for validation. `source`, `status`, and `customer` are deliberately **not** editable here — those only change through `quotation_form`'s `?query=` path / `query_not_interested`, so they can't drift out of sync with what those actions actually did.

- **Sending a quote from a Query** goes through `quotation_form?query=<pk>` (see "Quote form flow") rather than a dedicated view — creates or reuses a `Customer` from the query's company name (falling back to phone/`Query #pk` if no name yet), copies over email/phone if given, and — only once the quotation is actually **sent** (not on a draft save) — sets `query.customer` and `query.status = 'quote_sent'`. If the customer has an email on file it sends the real quote email (`_dispatch_quote_email`); if not, it shows a warning telling staff to use the existing "Copy Link" action instead. Both the Orders and Query dashboards' "Copy Link" button builds its URL from `_public_quote_base_url(request)` (same `PUBLIC_QUOTE_BASE_URL`-first logic `_dispatch_quote_email` uses) rather than the admin's own request host — a WhatsApp-sourced lead typically has no email, so this fallback link is the one most likely to actually reach an external customer, and building it from an admin's private Tailscale address would make it unusable. The dashboard's "📧 Send Quote" link stays available after a query reaches `quote_sent` too (alongside Copy Link/PDF), not just while it's `new` — so correcting a detail via `query_edit` (grade, size, company name, ...) after a quote already went out doesn't require admin access just to send a follow-up quote reflecting the fix; it's a template-level choice (`query_dashboard.html`), not a `status` reset, since `quotation_form` already works fine being re-entered against an already-`quote_sent` query.
- **The query's product code** is shown on its detail page from `Query.effective_product_code()` — the linked code, else the one its product type + grade point to (`matching_product_code()`), so a query the bot filled in shows `FBB009` without anyone saving the Edit page. The bot also links `Query.product_type` as soon as type and grade are both known (`_process_whatsapp_answer`), when the catalogue has the code.
- **Order numbers on the query:** once an order is placed from a query's quote (`Order.source_query`), the Query dashboard's Status cell shows "Order placed: ORD-0003" (several orders from one quote are listed together; the orders are prefetched, so no extra query per row) and the detail page has an "Order placed" row. The number is read live each time, so it follows the gap-closing renumbering when an earlier order is deleted (`Query.order_numbers()`).
- **`query_not_interested`** (staff-only, POST) — sets `status = 'not_interested'`, no email, just closes out the lead. Only offered while a query is still `new` — once a quote's been sent, the dashboard no longer shows this action (declining after already being quoted isn't a case the UI needs to handle specially; staff just don't act on it further).
- The customer's order form takes its items from the latest sent quotation (see "Quote form flow"); only in the no-quotation fallback does it pre-fill from whichever `Query` is in-flight for them (`Query.objects.filter(customer=customer, status='quote_sent').order_by('-created_at').first()`) — grade, size, quantity and notes show up already populated (still editable). **Sending a quote from a query** (`quotation_form?query=`) also pre-fills the quotation's *customer address* and *customer GSTIN* (two separate fields, `Quotation.customer_address` / `customer_gstin`) from the query's GST address and GST number, and the line-item description from what the query knows (`_query_item_description`: the product code if matched, else e.g. "Flat Bright Bar EN8D 50 x 6 mm"; the old free-text requirements answer is never used) — so what the bot collected reaches the printed quotation without retyping; all of it stays editable. For a quote to an existing customer (`?customer=`) with no query, the address and GSTIN come from the last quote sent to them, so a repeat quote doesn't start blank. On submission, `order.source_query` is set to that query and the query flips to `status = 'converted'`.

### WhatsApp Cloud API: staff-initiated intake bot (`/webhooks/whatsapp/`)

Staff never wait for a customer to message first. Logging a phone number on `/queries/` sends that number a WhatsApp message asking for their company name; once they reply, an automated back-and-forth collects, in this order, **company name → email → GST number & address → how many products (tap 1–5) → product type → drawing/sample → grade → width (mm) → thickness (mm) → make/mechanical properties/process → end use → delivery form → quantity in kgs → a summary the customer confirms or changes**, one question at a time, saving each answer straight into the `Query`'s real fields — not a freeform transcript. **The quantity question is just "Please enter the quantity in kgs."** (shortened on 2026-10-06; it used to also ask the frequency, and the frequency is no longer asked — the customer's order form still has a Frequency field). The reply must be a number in kg (`_parse_whatsapp_quantity_kg`: one number marked kg/kgs, or a single bare number); tons, quintals, several numbers or no number re-send "Please enter the quantity as a number in kgs, for example 8000." and don't advance, like width and thickness. It is saved in `quantity_text` as typed and as the number in `Query.quantity` (kg, which the quote form pre-fills; a quantity staff already entered is not overwritten while collecting). (Until 2026-10-05 quantity wasn't asked at all, since quoting is per-kg; it's now asked because the requirements questionnaire asks for it, on the client's request.) **Width and thickness are asked right after grade**, as two separate questions (decided 2026-10-06; a single size had been asked for a day before). Each reply is parsed as a number of mm (`_parse_whatsapp_dimension`: the first number, comma read as a decimal point, above 0, at most 3 decimals) and saved to `Query.width` / `Query.thickness`; with several numbers ("10 and 12 mm") the first is kept and the whole reply is added to `notes` for staff. A reply with no usable number ("as per drawing", "no") re-sends `WHATSAPP_DIMENSION_INVALID_MESSAGES[field]` and doesn't advance, like the GST question — a customer who can't give one is stuck until staff fill it in on the Edit page. **Multiple products:** the count (`item_count`, a tappable list `count:1`…`count:5`, `_parse_item_count`; typed "3"/"three" also work) is asked once, which creates that many `QueryItem`s. For one product everything is as before (tappable type list, Coil/Bar buttons). For N>1 each per-product question (`WHATSAPP_PER_ITEM_FIELDS`: type, grade, width, thickness, delivery form, quantity) is asked once and answered with **exactly N comma-separated values in the same order** (dots for decimals; `_parse_item_values`); a wrong number gives "I received 2 values but need 3, one for each product, separated by commas" plus the question again, and a bad value says "Product 2: …" — nothing is saved on any error. Drawing, make/properties/process and end use are asked once for the query (the exact split is to be confirmed with the company).

- **Hard constraint from Meta, not a design choice**: WhatsApp Business Cloud API refuses free-form messages to a number that hasn't messaged the business first (or has gone quiet 24h+) — the opening message must be a pre-approved **template**. `_send_whatsapp_template_message` sends template `matta_drawing_query_intake` when a query is logged; every question after the customer's first reply is sent as free-form text via `_send_whatsapp_text_message`, since their reply opens a 24-hour window. **The template itself must be created and approved in Meta Business Manager before any of this works** — submit it as a Utility-category template with body: *"Hi! Thanks for calling Matta Drawing Works. To prepare your quote, could you share your company name?"* (The legal/trading name is "Matta Drawing Works" — it's what the privacy policy and the customer-facing wording use. **The wording lives only in Meta's WhatsApp Manager, not in this repo**: if the approved template still says just "Matta Drawing", edit its body there — Meta re-reviews an edited template — or create a new template and change `WHATSAPP_QUERY_INTAKE_TEMPLATE` in `materials/views/whatsapp.py` to its name.) Meta's review can take anywhere from minutes to about a day.
  - **Language code gotcha**: a template is approved under the exact language code chosen in WhatsApp Manager's "Select language" dropdown — picking "English" approves it as `en`, not `en_US`, even though `en_US` looks like the obvious default. Sending with the wrong code fails with a `(#132001) Template name does not exist in the translation` error even though the template is real and approved — the fix is matching `WHATSAPP_QUERY_INTAKE_TEMPLATE_LANGUAGE` (`materials/views/whatsapp.py`) to whatever code the template actually shows in WhatsApp Manager → Message templates, not assuming `en_US`. Check via the Graph API (`GET /{whatsapp_business_account_id}/message_templates`) if it's ever unclear.
- **Phone numbers are normalized to digits-only** (`_normalize_phone`, strips everything but `[0-9]`) wherever they enter the system — both when staff type a number into `/queries/` (any human format: `+91 98765 43210`, `98765-43210`, ...) and when routing an inbound WhatsApp reply. Meta's `msg["from"]` is always bare digits, so without this the two would never string-match and every reply would spawn a duplicate orphaned `Query` instead of continuing the real one.
- **A phone number can only have one open query at a time**: `query_dashboard` rejects logging a second query for a number that already has one in `new`/`quote_sent` status, since a customer's replies only ever route to the newest match — a silent duplicate would orphan the older row forever.
- **Question sequence**: `WHATSAPP_QUERY_FIELDS` (`materials/views/whatsapp.py`) is the fixed order above — `_next_expected_query_field` returns whichever is still unanswered. There's no separate "stage" field; the next question is always inferred from the data itself, so it can't drift out of sync and tolerates a field getting filled some other way (e.g. a staff edit) mid-sequence. **One WhatsApp message maps to one field**, and several questions are deliberately combined to keep the conversation short (13 single-topic questions were cut to 9 on the client's request on 2026-10-05): GST number + address, make + mechanical properties + process (`technical_requirements`), (quantity + frequency was also combined once; frequency is no longer asked). End use and delivery form were merged at first and are separate questions again, because delivery form has only two answers and is asked with buttons. The combined answers are saved as typed — staff read and split them by eye, and a customer who answers only half of a combined question is accepted as done (staff follow up). `WHATSAPP_QUERY_QUESTIONS` holds the wording for every field except `company_name` (that's the opening template, see below) — edit it there. The answer fields are `Query.INTAKE_TEXT_FIELDS` (`gst_number`, `gst_address`, `technical_requirements`, `end_use`) plus the existing `contact_email`/`drawing_notes`; the per-product answers live on `QueryItem`. **"no" is a real answer**: a non-blank value is what marks a question answered, so a customer replying "no" to the make/properties/process question is saved as `no` and the sequence moves on. `contact_email` is validated before saving (`_is_valid_whatsapp_email`) — an invalid reply just re-sends the same question.
- **The GST reply is split into number and address** (`_parse_whatsapp_gst_details`), and is the one other validated answer. **A GST number is compulsory for every company, so there is no "NA" option** — it was offered briefly on 2026-10-05 and removed the same day on the client's say-so; the question wording doesn't tell the customer to send both in one message either (it just asks for the GST number and registered address). Accepted: a well-formed 15-character GSTIN alone (spaces and case ignored, saved upper-case and compacted), or a GSTIN anywhere inside a longer message — before or after the address, with or without a `GSTIN:` label (the label is only stripped when it sits right next to the number, so a street called "GST Road" keeps its name). Whatever isn't the number becomes `gst_address`. If the reply has no address (just the number), `gst_address` stays blank and the sequence's blank-inference asks for it with its own question — that fallback is why `gst_address` is still in `WHATSAPP_QUERY_FIELDS`. Anything without a valid GSTIN (including "NA", "no", "not registered") re-sends `WHATSAPP_GST_INVALID_MESSAGE` and doesn't advance, rather than saving a typo — which also means a customer who genuinely can't give one keeps getting that message until staff step in manually. Format only — the checksum would need the GST portal to verify. The GSTIN shape lives once, as `GSTIN_PATTERN` in `models.py`, shared by the model validator and the bot.
- **Questions with a fixed set of answers are sent as tappable reply buttons** (`WHATSAPP_QUERY_CHOICES`, currently just `delivery_form`: **Coil** / **Bar**, taken from `Query.DELIVERY_FORM_CHOICES`, which is also what gives the Edit page and admin their dropdown and rejects anything else on staff edits). `_send_whatsapp_question` is the one place that decides, per field, between `_send_whatsapp_buttons_message_background` (an Interactive `button` message: `type: interactive`, `interactive.action.buttons[].reply.{id,title}`) and the plain text sender; the background wrapper has the same fire-and-forget contract as the text one. Meta's limits are at most **3 buttons, each title up to 20 characters** (`test_choice_questions_fit_whatsapp_reply_button_limits` enforces it for anything added to `WHATSAPP_QUERY_CHOICES`). Like free-form text, a buttons message is only allowed inside the 24-hour window the customer's own reply opened — always true mid-sequence. A tap comes back as an inbound message of `type: interactive` with `button_reply.title` (or `list_reply.title`), which `_process_whatsapp_change` feeds into the same path as a typed answer. Typing instead of tapping still works: `_parse_whatsapp_delivery_form` accepts "coil", "Coils please", "bars" (case-insensitive, whole words) and normalises it; anything else, or an answer naming both, re-sends the buttons without saving. To add another button question: add the field to `WHATSAPP_QUERY_FIELDS`/`WHATSAPP_QUERY_QUESTIONS`, give it choices in `WHATSAPP_QUERY_CHOICES` (and `choices=` on the model field), and add a parse branch in `_process_whatsapp_answer`.
- **The drawing question accepts an image/PDF *or* a text reply (it's the fifth question, after the requirements)** — `Query.drawing` (a `FileField`, `upload_to='query_drawings/%Y/%m/'`) holds an attached file; `Query.drawing_notes` holds either the customer's plain-text reply (typically "no") or a short description if they described it instead of attaching. `drawing_notes` doubles as the "this question was actually answered" marker for `_next_expected_query_field` — a `FileField` alone can't distinguish "not asked yet" from "asked, customer had none," so the sequence checks `not query.drawing and not query.drawing_notes` for this one field instead of a plain blank check.
  - **Image/document replies are handled separately from text** (`_process_whatsapp_change` branches on the inbound message's own `type`) and only when 'drawing' is actually the field being asked for right now — an image arriving at any other point in the sequence, or with no in-progress query at all, is dropped, the same as any other unhandled message type. Downloading one is a real Graph API round trip: `_download_whatsapp_media` does the documented two-step fetch (resolve the media id to a short-lived signed URL + mime type, then download the bytes from that URL, both calls needing the access token) — `_process_whatsapp_drawing_media_background` runs that whole thing (download, save to `Query.drawing`, advance the sequence) in a background thread, for the same reason outbound follow-ups are backgrounded: Meta expects a fast webhook ack, well before either of those HTTP calls would finish. `connections.close_all()` at the end of that thread avoids leaking the DB connection it opened for itself, since Django only tears those down automatically at the end of a request/response cycle — which a background thread isn't part of.
- **The product type is a tappable list** (`product_category`, asked right after the GST details, then the drawing question; the free-text "Your requirements" question was dropped 2026-10-06 because it only existed to find the product type, which is now a tap): `_send_whatsapp_question` sends an Interactive **list** message (`_send_whatsapp_list_message`: `interactive.type: list`, one section of rows with `id` `category:<pk>`, a title up to 24 characters — a longer name is cut with "…" and carried in full in the row's description — and a "Choose type" button). Meta allows at most **10 rows**, which is why this wasn't possible with the old 14 types (it fell back to detecting the type in free text) and is with 7; if the owner adds more than 10, the bot falls back to asking the customer to type the name. A tap comes back as a `list_reply` whose id `_process_whatsapp_change` turns back into the full type name; a typed name works too (`_detect_product_category`: the full name, plus either half of a "Profile/Shaped"-style name, with a shorter name inside a longer match dropped and an ambiguous answer matching nothing); anything unrecognised re-sends the list. A type staff already set skips the question. The product *code* is matched later, on the quote or the query's Edit page, from type + grade (see "Quote form flow"). **Customised (company-specific) products are still an open design question:** the leading idea is an optional owning customer on `ProductType`, which depends on whether customised items are usually reordered by the same company.
- **The review at the end** (added 2026-10-06; `Query.bot_stage`, `_review_reply`): when the last question is answered the bot does **not** say thanks yet. It sends the answers as a summary (`• Company name: …`, one line per answer; `_summary_text`) and then, as a second message from the same thread so they arrive in order, "Is everything correct?" with two buttons, **Confirm** / **Change something** (`stage = 'summary'`). *Confirm* stores `intake_confirmed_at`, moves to `'done'` and sends the thanks (`WHATSAPP_CLOSING_MESSAGE`). *Change something* sends a tappable list of the 12 answers (two lists, since Meta allows 10 rows: the first 8 plus "More…", then the other 4 plus "← Back"; `pick_field` / `pick_more`); tapping one re-asks that question (`editing`, `edit_field`) — as a list or buttons for the product type and delivery form — and the new answer goes through exactly the same checking as the first time (`_parse_answer`: GSTIN, numbers in mm/kg, email, type name, Coil/Bar). A valid new answer is **held, not stored**: `Query.pending_value` (a replacement drawing file goes to `pending_drawing`) and `confirm_change` ask "Change width to: 75 mm — Save this change?" with **Yes, save it** / **No, keep old**. *Yes* stores it (`_apply_updates(editing=True)` — it also re-links the product code to the new type + grade, or drops the link if there is none) and shows the updated summary and the two buttons again; *No* (or typing "cancel") keeps the old value and shows the summary again. Typing works wherever a button or row is offered ("yes", "the thickness", "cancel"); anything not understood re-sends the current buttons or list. The only number of changes is the customer's. A message after `done` is added to `notes` as before; a query that finished before this existed (stage empty, all answered) behaves as it did. The detail page shows "Answers confirmed — by the customer on WhatsApp, <date>", or "Waiting for the customer to confirm their answers". The summary, the lists and the buttons are only sent while the 24-hour window is open (see the offline section below); the stage still moves on. **With several products** the summary lists `Product 1: …`, `Product 2: …`; Change something shows the query answers plus one row per product (`item:N`), and choosing a product opens a second list of its six details (`pick_item_field`, `edit_field` like `item:1:width`); the held change then applies to that product only (`_item_only`), with the product named in the question ("Product 2: …").
- **Follow-up sends happen off the request thread** (`_send_whatsapp_text_message_background`) — `_process_whatsapp_answer` saves the customer's answer synchronously, then fires the next question in a daemon thread rather than blocking the webhook response on the Graph API's own network round trip. Meta expects a fast ack; a slow outbound call inside the same request is exactly the condition that triggers Meta's own redelivery (see the limitation below). A send failure here is logged (`logger.warning`, not silently swallowed) since it means every later question in that conversation would otherwise stall with zero visibility — but it never blocks or loses the already-saved answer.
- **Read-then-write on a Query is done under `select_for_update()`** inside `transaction.atomic()` (`_process_whatsapp_answer`) — a no-op on SQLite (no row-level locking there, verified: doesn't raise, just doesn't lock), but real protection against two overlapping deliveries for the same phone racing each other into the wrong field if this ever runs on Postgres.
- **Fallbacks**: an inbound message with no matching in-progress `Query` (a cold message, or a reply after that number's query already converted/was marked not interested) still creates a bare `Query(source='whatsapp', ...)` rather than being dropped. A message that arrives after the sequence is already complete is appended to `notes` as a plain note rather than mistaken for a new answer.
- **Offline gaps, redelivery and ordering** (decided 2026-10-06; the app runs on one PC, and while it is off Meta can't deliver the customer's replies — it keeps retrying, then replays a backlog, late, repeated and in any order). Handled in `_process_whatsapp_change` and `_process_whatsapp_answer`:
  - **Repeats are skipped:** every handled message's Meta id is recorded in `WhatsAppMessage` (unique `message_id`, pruned after 30 days) and a seen id is ignored. The claim is released if handling raises, so Meta's retry of a failed delivery still works.
  - **A batch is handled oldest-first** (sorted by Meta's `timestamp`), and when one delivery holds several messages from the same customer **only the last one sends the next question**, so a replayed backlog doesn't make the customer answer a string of questions they already answered.
  - **A question is never asked twice:** `Query.last_asked_field` remembers the question sent and not yet answered (or `_done` for the closing message); `_advance_whatsapp_query` skips it if it's still the next one.
  - **An out-of-order reply isn't used as an answer.** A message older than the newest one already handled (`Query.last_inbound_at`, the customer's newest message *sent* time) is added to `notes` as `[late reply, sent …]` and the query is flagged. It can't repair a reply already saved into the wrong field before the late one turned up — that's what the flag is for.
  - **The 24-hour window:** WhatsApp only lets the bot send free-form text for 24 hours after the customer's last message (`WHATSAPP_WINDOW` is 23 h, with a margin). When a replayed message is older than that, its answer is still saved but nothing is sent (Meta would refuse it) and the query is flagged. Staff then message the customer on WhatsApp themselves (Business Suite); the bot carries on from the next unanswered question when they reply, because the next question is inferred from the data.
  - **Staff see it:** `Query.needs_review` / `review_note` show as a "⚠ Needs a look" badge on the Query dashboard and a card on the detail page with a "Mark as reviewed" button (`query_clear_review`, POST). The flag is never cleared automatically.
  - **No automatic "we'll reply shortly" while the PC is off** (decided 2026-10-07). Nothing running on the PC can answer while it is off, and the owner chose not to add an always-on service in front of it (a small Cloudflare Worker relay was written and tested on 2026-10-06, then removed unused — see git history before the commit that removed `relay/` if it is ever wanted). Customers simply get no reply until the PC is back; Meta then replays their messages and the handling above (repeats skipped, oldest first, one question at a time, 24-hour check, flag for staff) keeps the conversation consistent.
- **This is the app's second public, unauthenticated endpoint** (after the quote form) — Django's own auth plays no role, since Meta's servers never carry a session or CSRF cookie:
  - **GET** (`_whatsapp_verify`) — the one-time subscription handshake. Confirms `hub.mode == "subscribe"` and `hub.verify_token` matches `WHATSAPP_VERIFY_TOKEN` (constant-time compare), echoes back `hub.challenge`. An unset `WHATSAPP_VERIFY_TOKEN` fails closed — it never "verifies" a request, even one that also omits `hub.verify_token`.
  - **POST** (`_whatsapp_receive`) — verifies `X-Hub-Signature-256` as an HMAC-SHA256 of the *raw* body, keyed with `WHATSAPP_APP_SECRET`, **before** the body is parsed at all. `@csrf_exempt` is safe here specifically because this signature check is the real authentication, not Django's CSRF middleware. An unset `WHATSAPP_APP_SECRET` fails closed too — the check explicitly refuses to validate anything rather than computing an HMAC keyed with an empty (attacker-known) string, which would otherwise make the signature trivially forgeable.
  - `value.statuses` (delivery receipts) are ignored, not treated as messages; text messages and reply-button taps are always handled, image/document replies only when they're answering the drawing question (see above), and every other message type (audio/video/location/etc.) is still not handled. A syntactically-valid but non-object JSON body (e.g. a bare array) is also acked and ignored rather than raising.
- **Env vars** (`.env`): `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET` (as before) plus `WHATSAPP_ACCESS_TOKEN` (a permanent System User token from Meta Business Manager, scoped to `whatsapp_business_messaging`) and `WHATSAPP_PHONE_NUMBER_ID` (the numeric ID Meta assigns the connected number) — the two new ones are what actually let the app send messages, guard them like any other API secret.
- **Meta-side setup** (manual, outside this codebase): register `https://<funnel-hostname>/webhooks/whatsapp/` (e.g. `https://mdw.tail2734e7.ts.net/webhooks/whatsapp/`) as the webhook callback URL, enter the `WHATSAPP_VERIFY_TOKEN` value, subscribe to the `messages` field, and separately submit + get approval for the `matta_drawing_query_intake` template described above.
- **Exposing it publicly**: like the quote form, this endpoint needs its own Tailscale Funnel path on the deployment machine, alongside the existing `/quote` one:
  ```
  tailscale funnel --bg --set-path /webhooks/whatsapp http://localhost:8000/webhooks/whatsapp
  ```
- `quotation_form` is still the only thing that emails a customer — WhatsApp here is intake-only, not quote delivery.

### Generated product codes (`materials/product_codes.py`)

**A product code is a product type + a grade — size is not part of it** (decided 2026-10-06: width and thickness vary per order, "no set sizes"; this replaced the earlier type + grade + size code, which had been `FBB00100120`). `FBB009` is Flat Bright Bar in EN-8D:

| Part | Example | Meaning |
|---|---|---|
| 3 letters | `FBB` | the product type's code (`ProductCategory.code`) |
| 3 digits | `009` | the grade's number (`GradeOption.number`) |

**Product codes are created in the Django admin, never by a quote.** Staff add one under *Product codes → Add* with product type + grade (both required) and leave Item Code blank; Item Code is the first field and is generated on save. **A quote only looks a code up** — if type and grade are chosen and no code exists, sending is refused until the admin adds it. `UniqueConstraint(category, grade)` keeps one code per type + grade (a second, conditional one covers older codes with no type). Migration `0044` dropped `ProductType.size` and rewrote the one live code `FBB00900120` → `FBB009`; it refuses to run if two codes would collapse into the same type + grade.

- **One module owns the format** (`product_codes.py`): `describe_product_code` (the existing code, or the code that would be generated, or why none can be — read-only), `item_code_for` (the code for the admin form, or the reason none can be; refuses a duplicate), `reserve_grade_number`, `canonical_grade`, `grade_key`, `find_product_code`. Nothing else builds a code string.
- **Every grade is stored as capital letters and digits only** (decided 2026-10-06: "no hyphen in any, no spaces at all, everything in caps"): `EN-8D`, `en 8d` and `EN8D` are all `EN8D`; `EN-8D CR` is `EN8DCR`, `SAE 1008` is `SAE1008`. It is enforced by `GradeField` (`models.py`, with `normalize_grade`) on every grade column — `GradeOption.name`, `Material`, `GateEntryLot`, `AllowedCoilSpec`, `ProductType`, `Order`, `Query`, `QuotationLineItem` — which normalizes when a form/model is cleaned and again on save, so it holds whichever way a grade arrives (admin, quote form, bot, spreadsheet import, shell); `QuerySet.update()` bypasses it. Migration `0046` converted the existing data (list entries that normalize to the same grade were merged, keeping the first and its product-code number). The browser scripts (quote form, query edit, admin) normalize as you leave the grade box (`normalizeGrade`). `grade_key()` (lower-case of the same rule) is still what lookups compare, via `find_grade_option`/`find_product_code`/`_match_product_type(grade, category)`, and `canonical_grade()` is just `normalize_grade`. `manage.py merge_grades "8620=SAE8620" ...` (dry-run by default, `--apply` to change) merges genuinely different strings for the same steel — spelling differences of punctuation and case can no longer arise — and rewrites every record that has the grade; use it **before** the grade is first used in a code, because a grade number is permanent. Coil-picking spec matching (`AllowedCoilSpec` vs a coil's grade) is a plain case-insensitive compare, which is now enough.
- **Grade numbers are handed out automatically the first time a grade is used in a code, then kept forever** — a code already printed on a document never changes meaning. An unknown grade is added and given the next free number; one that exists without a number is numbered on first use. The number is reserved when the admin saves the code (`ProductTypeAdmin.save_model`); a preview for a brand-new grade shows the next free number *now*. The number is editable in the admin (unique).
- **In the admin** (`ProductTypeAdminForm`, `materials/static/materials/admin_product_code.js`): as type and grade are filled in, the script fetches `product_code_lookup` and fills Item Code live (it never overwrites a hand-typed code) and warns if the combination already has one. The grade box is a type-ahead (`<datalist>` of `GradeOption` names, not a picker), tidied to the listed spelling. The add page accepts `?category=&grade=` to open prefilled. A hand-typed code is kept and takes no grade number.
- **On the quote form:** once type and grade are filled in and no code matches, the hint reads "No product code for this yet…" with an "Add it in the admin before sending" link (from `add_url` in the lookup response). **Send is refused** with "Can't send yet — no product code exists for: …" and a `➕ Add product code` link per missing item, opening the admin prefilled; nothing is created and the typed form is kept. **Save Draft is never blocked**, and items without a type and grade, or with a code picked by hand, are fine. `product_code_lookup` (`/product-codes/lookup/`, staff-only, returns **403 JSON** rather than a redirect, never creates anything) means the format exists once, in Python — not duplicated in JavaScript.
- If a hand-made code already uses the generated text (without a type), the new one gets a `-2` suffix rather than clobbering it.
- **Checks:** none of the Python tests run JavaScript, and a dropped parenthesis once silently disabled this form's matching and preview, so `InlineScriptSyntaxTests` (`test_templates.py`) pulls the inline `<script>` blocks out of the main staff pages and runs `node --check` on them (skipped where Node isn't installed — it is on GitHub's runners and a normal dev machine). It only parses; behaviour was verified in a real browser against a throwaway local copy of the app (`manage.py runserver` with a scratch database).

### Width and thickness (product side)

On everything on the **product side** — `Query`, `QuotationLineItem` and `Order` — the single size is now two fields, **`width` and `thickness`** (mm, `Width (mm)` / `Thickness (mm)`; migration `0044` renamed the old `size` to `width` and added `thickness`). Raw coils, gate-entry lots and `AllowedCoilSpec` still have one `size`. The quote form requires both to send (a draft doesn't), the WhatsApp bot asks both (below), the customer's order form shows both locked from the quote line, the query detail/edit pages and the PDF description (`50 x 6 mm`) show both, and the API's order fields are `width`/`thickness`. Neither is part of a product code. ("Thickness" is the word the owner used last; it could be renamed "height" in the labels if preferred.)

## Quote form flow

Staff finalize the deal with the customer directly (phone/WhatsApp) before sending anything — Send Quote is no longer a bare link. Every Send Quote action, from any entry point, funnels into one page: **`quotation_form`** (`/quotations/new/`, `materials/views/quotations.py`), reached three ways:

- **`?query=<pk>`** — from the Query dashboard's "Send Quote" button. The company name is fixed (comes from the `Query`), and one item row pre-fills from the query's `product_type`/`grade`/`size`/`quantity`.
- **`?customer=<pk>`** — from the Orders dashboard's per-customer "Send Quote" link, re-quoting an existing customer.
- **neither** — from the Orders dashboard's "New Order" card's "Send Form to Them" button, for a brand-new company; the page collects name/email/phone itself (carried over from whatever was already typed into that card's own fields, via GET params, rather than lost on navigation).

The form itself: a customer section (read-only or editable depending on how it was reached), a **repeatable line-item formset** (`QuotationLineItemFormSet` in `materials/forms.py`, the same "collapsible repeatable row + JS add/remove/reindex" pattern `GateEntryLotFormSet` already established for gate entry lots) — description, product type, grade/size, quantity, unit, rate/kg, discount%, HSN/SAC, GST%, tool cost, MOQ per row, at least one required to actually send — and a collapsed-by-default "More details" section for the header fields (`QuotationForm`: ref/rev numbers, sales person, kind attn, subject, customer address, same-state-as-us GST toggle, freight/P&F amounts, and the seven Terms & Conditions fields, all pre-filled with the client's standard wording but editable). A GET request never creates or changes anything, even with `?query=` set or a draft pk in the URL — the Query/Customer resolution (creating/reusing a `Customer`, flipping `query.status` to `quote_sent`) only happens on a successful POST, and only when actually sending (see below).

**Two submit buttons, one form: Save Draft vs. Send.** `quotation_form` reads `action` from the POST (`'save_draft'` or `'send'`, defaulting to `'send'`):
- **Send** is the strict, original path — full form + formset validation (`.is_valid()` on both), an invalid submission creates nothing. On success, `Quotation.status` becomes `'sent'`, which is the only thing that ever assigns `quotation_no` (see the `Quotation`/`QuotationLineItem` model bullets above), then `_dispatch_quote_email` fires — the official **PDF quotation** attached, and the email body lists each item with its product type (`QuotationLineItem.spec_text()`, the same `Product type / Grade / W x T mm` line the PDF prints) (`materials/pdf.py::generate_quotation_pdf`), with the order-form link underneath as "if you wish to proceed, fill this in."
- **Save Draft** is deliberately lenient — no formset validation at all. Line items are instead parsed by `_parse_draft_line_items` (`materials/views/quotations.py`) straight off the raw POST: a row with a description but no quantity/rate yet still saves (both are nullable on `QuotationLineItem` specifically for this), a row with no description is just dropped, and a draft can exist with zero line items. `Quotation.status` stays `'draft'`, so no `quotation_no` is consumed and no email is sent — just a `messages.success` and a redirect back into edit mode. A draft's `Customer` is still created/reused immediately (the FK isn't nullable), but if it came from a `Query`, that `Query`'s own `status`/`customer` fields are **not** touched until the quotation is actually sent — a draft hasn't gone out to anyone yet.

**Resuming, listing, and discarding drafts.** The same `quotation_form` view also handles `/quotations/<pk>/edit/` (`quotation_edit` — same view, called with a `pk`) to resume an existing draft: `get_object_or_404(Quotation, pk=pk, status='draft')` (a 404, not a redirect, if that quotation's already been sent — sent ones are immutable, no edit path exists for them). GET pre-fills every field, including each line item, from what's actually stored; POSTing either updates the draft in place (Save Draft again) or finalizes it (Send — flips `status`, assigns `quotation_no`, deletes and recreates its line items from the now-validated formset, dispatches the email). `/quotations/drafts/` (`quotation_drafts`) lists every in-progress draft with Resume/Discard actions; discarding (`quotation_discard`, POST-only) hard-deletes it outright — safe, since a draft never consumed a `quotation_no` in the first place, so there's no gap to worry about.

**The header fields show what was saved or prefilled.** The "More details" inputs read from the template's `post` dict, which `quotation_form` fills from the POST on an error and otherwise from `_saved_values(form)` (a draft's saved values, or the prefill; dates as ISO strings for `<input type="date">`; a new quote starts with the in-state box ticked). Until 2026-10-05 that dict was empty on every normal page load, so **resuming a draft showed every header field blank — and saving again would have overwritten the saved values — and the query's address/revision prefills never appeared on screen**; the earlier tests only checked `form.initial`, never the rendered HTML, which is why it went unnoticed (`QuotationHeaderValuesTests` now checks the page). **Re-sending prefills the revision.** Opening the quote form (`?query=`) for a query that already has a sent quote pre-fills the header's Rev. number (1, 2, …) and Rev. date (today), which print on the PDF as "Rev. 1 07/10/2026"; both stay editable. **Product code is matched, never chosen.** Each quote row has a **Product Type** picker (one of the 7), then grade, **width and thickness** (both required to send), and the **Product Code** is matched from type + grade — the owner doesn't pick it, and width and thickness don't affect it. On the form this happens live (client-side, from a type+grade→code map embedded as JSON: grade by `gradeKey`; changing the type or grade re-matches; a no-match clears an auto-selected code; **a code picked by hand is never overridden**), and the server does the same on Send and Save Draft (`_autofill_product_codes` → `common._match_product_type(grade, category)`) so a code is set even without JavaScript. With **no type chosen, the grade only matches when exactly one code has it** — two codes sharing a grade across different types is ambiguous, so it matches nothing rather than guessing (the order's code is then assigned at confirmation). When reached with `?query=`, the Customer card also shows the query's product type, product code (`Query.effective_product_code()`, or "none in the catalogue yet") and grade · width × thickness, and the first row's code is pre-selected server-side, not left to the JavaScript. The query's product type, grade, width, thickness and quantity pre-fill the first row, so for a query-originated quote the owner mostly just sets the rate. If the combination has no code, **Send is refused** until the admin adds one (see "Generated product codes"); quotes never create codes. This replaces the bot's old auto-match, which couldn't work once size stopped being asked on WhatsApp.

**The customer's order form** (`quote_form`, `/quote/<token>/`) reads from the **latest `sent` quotation** for that customer (drafts are ignored). Each quoted item gets its own block showing its **product type, product code, grade, width and thickness locked** (the code is the quoted one, else the catalogue's code for the item's type + grade — `item.shown_code`, set in the view and also what the order gets — and "To be assigned" when there is none; the type is the line's, else the code's) — they aren't inputs, and the server ignores anything posted for them, taking them from the `QuotationLineItem` — with quantity pre-filled from the quote (editable), **end usage and delivery form pre-filled from the in-flight query** (`query.end_use` / `query.delivery_form`, lower-cased to the order's `coil`/`bar` values — so the customer isn't asked twice what they told the bot; both stay editable, and nothing is pre-filled when there's no query; the bot's make/properties/process answer is one block of text and can't be split into the order form's three separate fields, so it isn't pre-filled), plus the optional detail fields (delivery form, frequency, mill make, **Attach Drawing**, mechanical properties, **Tolerance**, processes, end usage, delivery date, notes). **The drawing is an attachment, not a typed box** (decided 2026-10-06): `Order.drawing_file` (`order_drawings/%Y/%m/`; allowed types pdf/png/jpg/jpeg/webp/dwg/dxf/step/stp/igs/iges/zip and at most 10 MB, checked server-side by the model's validators because the form is public; a refused file shows an error and doesn't burn the link). The hint under the box reads "Please attach the final dimension drawing." If the customer already sent a drawing on WhatsApp (`Query.drawing`) it is still copied onto each order that has none attached, but the form no longer mentions WhatsApp (decided 2026-10-07: they are just asked for the final drawing). **Tolerance** is a block under the item's spec: *Width 50 mm — From [ ] To [ ]*, *Thickness 6.5 mm — From [ ] To [ ]* (`width_tol_from/to`, `thickness_tol_from/to`, signed decimals kept exactly as typed — limits like 49.95 / 50.05 or offsets like -0.05 / +0.05), and a box for any other tolerance (`other_tolerances`); `Order.tolerance_lines()` reads them back ("Width 49.95 to 50.05 mm"). **Delivery form asks for what goes with it** (2026-10-07): choosing **Bar** shows *Length (mm) \** and a *Length tolerance From / To*; choosing **Coil** shows *Approx. Coil Weight (kg) \** (`Order.bar_length`, `length_tol_from/to`, `coil_weight`). The matching block is shown/enabled by a small inline script (and shown for both when JavaScript is off), the server requires the one that goes with the chosen form (`DeliveryDetailsMixin` in `forms.py`, error "Item 2: Please enter the bar length in mm.") and drops the other, and with no delivery form chosen neither is asked. The length tolerance is part of `Order.tolerance_lines()`, and `Order.delivery_detail_text()` ("Bar, 3000 mm long" / "Coil, approx. 2000 kg") is what the Orders details row and the confirmation email show. The old typed `Order.drawing_dimensions` stays on the model for older orders and the staff entry card, but the customer form no longer offers it. Staff see the drawing link and tolerances in the order's details row on `/orders/` and in the admin (Order → Tolerances, "Open drawing"), and the confirmation email lists them. **Submitting creates one `Order` per quoted item** (atomically), all linked to the source query; a single PO upload is attached to every one of them. The customer never has a code dropdown. Tampering is rejected rather than trusted: each block carries a hidden `line_item` id that must match the quotation's items in order, so a stale, swapped, dropped or foreign item gives an "out of date — reload" error and creates nothing. An item with no catalogue code (no matching type + grade) creates its order with no code, to be assigned when staff confirm it, since an order can't be confirmed without one. **Fallback (`CustomerOrderForm`):** a customer with no sent quotation (an old link from before quotes existed) gets the previous single free-form order — still with no code dropdown, the code matched from the product type they pick (a dropdown of the types, pre-filled from the query) and the grade they type, with width and thickness inputs. The quantity is labelled "kgs only" on both forms, as on the bot. No new rule enforces "orders only come after a query" (decided 2026-10-05: describe, don't enforce) — normal orders arrive query → quote → order, and a repeat order comes from re-quoting an existing customer, with the form pre-filling from that latest quote either way. As before, order → status `pending`, linked back via `source_query` if applicable, the PO is optional, and the link is **single-use**: the token regenerates after a successful submission, so the old URL is a 404 (a failed submission doesn't burn it). **The quote email says so** ("personal to your company and can be used once, to place the order for this quotation. For any later order we will send you a new quotation and link") — it used to say "unique to your company", which read like a permanent link and wasn't true; `test_email_says_the_link_is_single_use_not_a_standing_link` guards the wording. A reusable link for repeat customers was considered and not built (a link that never expires is a standing credential for placing orders).

If the customer has no email on file, staff fall back to the existing "Copy Link" action or a direct PDF download (`/quotations/<pk>/pdf/`, staff-only) to send the quotation manually — the `Quotation` record is still created either way, so what was quoted is always on file even when email delivery isn't available.

### Order confirmation email

When staff **confirm an order** (`order_confirm`), the customer is emailed "Order confirmed — <company>" (`_send_order_confirmation_email` in `views/orders.py`): "Your order has been confirmed. Production will start shortly.", the item as `Product type / Grade / W x T mm — N kg` (`Order.spec_text()`, same line as the quote PDF), the product code, delivery form and expected delivery date when set, and the company's phone/email, **with the complete order as a PDF attached** (`order_pdf.py::generate_order_summary_pdf`, widened 2026-10-07 from a short summary to the full record, after "show the complete order details"): a header with the placed and confirmed dates, the item count, the order number and the quotation number; the customer (email, phone, and the GST number and address they gave on WhatsApp); then per item every row the order page shows — order no., status, product type, code, grade, width, thickness, quantity, delivery form with its length or approximate weight, expected delivery, frequency, tolerances, mechanical properties, processes, end usage, mill make, notes, and whether a drawing and a purchase order came with it — **a dash where nothing was entered**, plus the typed dimensions only for older or staff-entered orders. It is one page for a normal order, never stored, regenerated each time, and carries the `ORD-####` number as it is at that moment (numbers close up if an earlier order is later deleted). It goes to `Customer.email`; with none on file, or without mail settings, or on a mail error, the order is **still confirmed** and staff get a warning message instead (a failure is logged). One email per order, since orders are confirmed one at a time. Nothing is emailed when the customer *places* the order (decided 2026-10-06, and again 2026-10-07 when the summary PDF was added: it "is only sent when we click Confirm") — the only other email is the quote email. Order numbers (`ORD-####`) are deliberately not in it: they can change when an earlier order is deleted.

### Official PDF quotation

`materials/pdf.py::generate_quotation_pdf(quotation)` renders the PDF via reportlab's `Platypus` flowables — chosen specifically because it's a pure-Python wheel with no system dependency (unlike e.g. WeasyPrint, which needs GTK/Cairo), since this app deploys on Windows via `waitress`. The PDF is never stored — regenerated fresh every time it's needed, from the `Quotation` record's own fields, its `line_items`, and the `COMPANY_*` settings. Layout mirrors the client's real, pre-app quotation format, restyled to this app's own accent-blue look: a company "logo" mark + Quote No./Ref No./Rev No. header, a "Quotation by" box (full company letterhead — address/phone/email/website/GSTIN — lives here, not duplicated in the header) paired with a "Quotation to" box (both boxes list rows in the same order: name, address, GSTIN, email, phone, then extras like website/sales person/kind attn; the customer box is name, **address and GSTIN** — the same rows our own details have — then email/phone), an itemized table (one row per `QuotationLineItem`, its description followed by a grey line `Product type / Grade / W x T mm` — the type from the line, else from its product code — with HSN/SAC/Qty/Rate/Disc%/GST%/Tool Cost/MOQ/Amount), Terms & Conditions and the CGST/SGST/IGST/Total breakdown side by side (not stacked — that's what keeps a normal quote on one page), and an amount-in-words line. **There is no signature block**: the quotation is system-generated and sent as is, so where the "Authorized Signatory" box used to be it says *"This is a computer-generated quotation and does not require an authorised signature."* (`QuotationPdfSignatureTests` checks the note is there and the signatory text is gone, by rendering with `reportlab.rl_config.pageCompression = 0` so the text is readable). The printed date is `sent_at`, falling back to `created_at`. Those `COMPANY_*` env vars default to blank except `COMPANY_NAME` — deliberately, so an unfilled-in PDF looks obviously incomplete rather than silently emailing a customer placeholder business details; fill them in with real values (`inventory/.env.example` has the full list, including `COMPANY_WEBSITE`) before this goes out to an actual customer.

Uploaded files (customer Purchase Orders in `Order.purchase_order`, WhatsApp drawings in `Query.drawing`) live under `MEDIA_ROOT` and are served by `materials/views/media.py::serve_media` at `/media/<path>` — **staff-only** (`@staff_required`, anonymous requests bounce to the admin login), since these are customer documents. It is deliberately *not* Django's `static()` URL helper, which silently returns no routes when `DEBUG=False` (so, until 2026-10-05, every upload link 404'd in production, contrary to what this section used to claim) and would be unauthenticated anyway; WhiteNoise only serves `STATIC_ROOT`. Only PDFs and `.jpg/.jpeg/.png/.webp` are shown inline — any other extension is forced to download (`Content-Disposition: attachment`), because the public quote form's PO input only restricts types via a browser-side `accept=` attribute, so a customer could upload an `.html`/`.svg` that would otherwise run on this app's own origin when staff opened it. Path traversal is refused by Django's `serve` (400/404). `inventory/media/` is gitignored, same as `db.sqlite3` — it's real customer data on the deployed machine, not something that belongs in the repo, and the nightly `backup_db` mirrors it into `db_backups/media/` (see the deployment section).

## REST API (`materials/api.py`, `materials/serializers.py`)

Read-only DRF API under `/api/` — `orders`, `coils`, `jobs`, `product-types`. Staff-only (`IsAdminUser`, session auth — same login as `/admin/`). Deliberately read-only: the state-transition rules (product type required to confirm, sequential step unlock, atomic pick creation) live in the `materials/views/` package and aren't re-implemented here — this surface is for reading data out, not changing it. `coils` supports `?remaining=true` and `?include_archived=true` (archived coils excluded by default); `orders` and `jobs` support `?status=`; `product-types` (the product *codes*) includes each code's `category` (the product type's name). `jobs` also supports `?order=<id>` and exposes `coil_no`/`weight_allocated` (from its `OrderCoilPick`). Browsable API login at `/api-auth/`.

## Tests, lint and CI

`.github/workflows/tests.yml` runs on every push/PR to `main`: `ruff check .` → `manage.py check` → `makemigrations --check` → the full test suite, on Python 3.12 (matching production), installing `requirements-dev.txt`. Run the same locally with `ruff check .` (from the repo root) and `python3 manage.py test materials` (from `inventory/`).

**Tests are a package, one module per area** (`materials/tests/`; `tests.py` was a single ~3,700-line file until 2026-10-05). `manage.py test materials` discovers every `test_*.py` in it:

`ruff.toml` is deliberately small — `E4`, `E7`, `E9`, `F` only (syntax errors, undefined names, unused imports/variables, ambiguous names, one-statement-per-line), not style. Migrations, `staticfiles/`, `media/` and `db_backups/` are excluded.

## Commit style

No `Co-Authored-By` trailers in commit messages.
